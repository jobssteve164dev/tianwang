## 2. 核心实现 (Core Implementation)

### a. 方法论/设计思路
通过分析完整的启动日志，发现问题的根本原因是脚本的进程清理逻辑存在缺陷，导致之前启动的服务端进程没有被正确清理，新启动的服务端进程无法绑定已被占用的端口。采用了"先清理进程，再清理端口"的双重清理策略，并完善了进程检测模式。

### b. 主要变更文件 (Key Changed Files)
*   `MODIFIED`: `dev.sh` - 修复依赖检测逻辑和进程清理逻辑

### c. 关键代码片段 (Optional but Recommended)

**修复依赖检测逻辑**
```bash
# 检查根目录依赖 - 使用更智能的检查方法
if [ -f "package.json" ]; then
    if [ ! -d "node_modules" ] || [ ! "$(ls -A node_modules 2>/dev/null)" ]; then
        missing_deps+=("根目录依赖")
        need_install=true
    elif [ -f "package-lock.json" ] && [ "package.json" -nt "package-lock.json" ]; then
        missing_deps+=("根目录依赖(package.json已更新)")
        need_install=true
    fi
fi
```

## 6. 问题根因分析 (Root Cause Analysis)

### 原始问题
1. **依赖检测误报**：脚本每次启动都提示需要安装依赖
2. **服务端启动失败**：端口 5555 被占用，导致新服务端进程无法启动

### 根本原因
1. **进程检测不完整**：清理脚本的进程名称模式 `"node.*server/src/index.js"` 无法匹配到在 `server` 目录下启动的进程 `"node src/index.js"`
2. **清理时机问题**：脚本只清理有PID文件记录的进程，但之前启动的进程没有对应的PID文件
3. **依赖检测逻辑缺陷**：过于严格的时间戳检查，导致误报

### 解决方案
1. **完善进程检测**：添加 `"node.*src/index.js"` 模式匹配
2. **增强清理逻辑**：在端口清理阶段就进行进程清理
3. **优化依赖检测**：只在真正需要时才提示安装依赖

## 7. 技术细节 (Technical Details)

### 修复的具体问题
1. **进程名称模式匹配**：
   - 原模式：`"node.*server/src/index.js"`
   - 新增模式：`"node.*src/index.js"`
   - 原因：进程在 `server` 目录下启动时，命令为 `node src/index.js`

2. **清理策略优化**：
   - 原策略：只清理有PID文件的进程
   - 新策略：先清理所有匹配的进程，再清理端口占用

3. **依赖检测逻辑**：
   - 原逻辑：`[ ! -f "package-lock.json" ] || [ "package.json" -nt "package-lock.json" ]`
   - 新逻辑：`[ -f "package.json" ] && ( [ ! -d "node_modules" ] || [ ! "$(ls -A node_modules 2>/dev/null)" ] || ( [ -f "package-lock.json" ] && [ "package.json" -nt "package-lock.json" ] ) )`

### 测试验证
- 进程检测：`pgrep -f "node.*src/index.js"` 成功返回 PID 61859
- 清理验证：清理后进程已终止，端口已释放
- 依赖检测：修复后不再误报依赖更新
